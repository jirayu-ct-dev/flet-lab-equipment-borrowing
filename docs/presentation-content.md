# เนื้อหาสำหรับสไลด์นำเสนอ: ระบบยืม–คืนอุปกรณ์

โครงสร้างนี้เสนอ 16 สไลด์สำหรับการนำเสนอประมาณ 12–18 นาที เนื้อหาทุกข้ออ้างอิงจากสิ่งที่ตรวจสอบได้ใน repository หากนำไปใช้จริงควรเติมชื่อสถาบัน รายวิชา ผู้จัดทำ และผลประเมินจากข้อมูลภายนอกโปรเจกต์

## สไลด์ 1 — ชื่อโครงงาน

**หัวข้อบนสไลด์**

- ระบบยืม–คืนอุปกรณ์
- Equipment Lending System
- เว็บแอปพลิเคชันสำหรับสาขาวิทยาการคอมพิวเตอร์
- ชื่อผู้จัดทำ / รหัสนักศึกษา / อาจารย์ที่ปรึกษา — *ไม่พบข้อมูลในโปรเจกต์ ต้องเติมภายหลัง*

**ภาพที่แนะนำ**: ภาพหน้า dashboard หรือหน้าเข้าสู่ระบบของระบบจริง

## สไลด์ 2 — ที่มาและแนวคิดของโครงงาน

**เนื้อหาบนสไลด์**

- รวมข้อมูลผู้ใช้ อุปกรณ์ และการยืม–คืนไว้ในระบบเดียว
- ติดตามอุปกรณ์ในระดับรายชิ้นด้วย asset code และสถานะ
- ออกแบบเป็น MVP ที่มีขั้นตอนสั้นและค้นหาข้อมูลเป็นหลัก
- เชื่อม LINE สำหรับเข้าสู่ระบบและรับการแจ้งเตือน

**หมายเหตุผู้นำเสนอ**: ไม่ควรกล่าวว่าระบบเดิมใช้กระดาษหรือ Excel เว้นแต่มีหลักฐานเพิ่มเติม เพราะ repository ไม่ได้ยืนยันข้อมูลดังกล่าว

## สไลด์ 3 — ปัญหาที่ระบบต้องจัดการ

**เนื้อหาบนสไลด์**

- ต้องจัดการข้อมูลโดยไม่แก้ฐานข้อมูลด้วยตนเอง
- ต้องป้องกันอุปกรณ์ชิ้นเดียวถูกยืมซ้อน
- รายการเดียวมีหลายอุปกรณ์และอาจคืนไม่พร้อมกัน
- ต้องจำกัดสิทธิ์และแยกข้อมูลของผู้ยืมแต่ละคน
- ผู้เกินกำหนดต้องไม่สามารถยืมเพิ่ม
- ต้องตรวจไฟล์ผู้ใช้จำนวนมากก่อนนำเข้า

**ภาพที่แนะนำ**: แผนภาพ “ข้อมูลผู้ใช้ + อุปกรณ์ + ธุรกรรม → ระบบกลาง”

## สไลด์ 4 — วัตถุประสงค์

**เนื้อหาบนสไลด์**

1. พัฒนาเว็บแอปสำหรับจัดการยืม–คืนอุปกรณ์
2. จัดเก็บข้อมูลอย่างเป็นโครงสร้างและตรวจสอบย้อนหลังได้
3. รักษาความถูกต้องของสถานะด้วย validation และ transaction
4. รองรับการยืมหลายชิ้นและคืนบางส่วน
5. แบ่งสิทธิ์ Admin และผู้ยืม
6. เพิ่มช่องทาง LINE และ import CSV/XLSX

## สไลด์ 5 — ขอบเขตและสิ่งที่ไม่อยู่ในระบบ

**ฝั่งซ้าย: อยู่ในขอบเขต**

- ผู้ใช้และข้อมูลสังกัด
- ชนิดอุปกรณ์และอุปกรณ์รายชิ้น
- ยืมหลายชิ้น คืนบางส่วน ประวัติ
- Dashboard และการค้นหา
- LINE Login / LINE notification
- Import CSV/XLSX

**ฝั่งขวา: นอกขอบเขต**

- คำขอยืม การจอง การต่ออายุ
- อนุมัติหลายขั้น
- ชำรุด สูญหาย ค่าปรับ ชำระเงิน
- audit log และ retry queue
- production scale และ distributed system

## สไลด์ 6 — ผู้ใช้งานและบทบาท

| ผู้ดูแลระบบ | ผู้ยืม |
| --- | --- |
| จัดการผู้ใช้และข้อมูลอ้างอิง | ดูข้อมูลของตนเอง |
| จัดการอุปกรณ์ | ดูอุปกรณ์พร้อมยืม |
| สร้างรายการยืมและรับคืน | ดูรายการและประวัติของตน |
| ดูประวัติรวมและ import ผู้ใช้ | เปลี่ยนรหัสผ่านและจัดการ LINE |

**หมายเหตุผู้นำเสนอ**: ผู้ยืมประกอบด้วยนักศึกษา อาจารย์ และเจ้าหน้าที่ แต่ใช้สิทธิ์การยืมชุดเดียวกันใน MVP

## สไลด์ 7 — ความสามารถหลักของระบบ

**เนื้อหาบนสไลด์**

- Authentication: username/password, persistent session, LINE Login
- User management: เพิ่ม แก้ไข ปิดใช้งาน รีเซ็ตรหัส และ import
- Reference data: คณะ สาขา รุ่น หมู่เรียน หมวดอุปกรณ์
- Equipment: ชนิดอุปกรณ์และอุปกรณ์รายชิ้น
- Lending: หลายชิ้นต่อรายการ ตรวจ overdue และสถานะอุปกรณ์
- Return: คืนบางส่วนและปิดรายการอัตโนมัติ
- History & dashboard: แยกตามสิทธิ์
- LINE: ยืมสำเร็จ เตือน 3/1 วัน และคืนครบ

## สไลด์ 8 — Flow การยืมอุปกรณ์

```text
Admin เลือกผู้ยืม
        ↓
ค้นหาและเลือกอุปกรณ์พร้อมยืมหลายชิ้น
        ↓
กำหนดวันยืมและวันครบกำหนด
        ↓
ตรวจ active / overdue / duplicate / availability
        ↓
บันทึก loan + items + เปลี่ยนสถานะใน transaction เดียว
        ↓
แจ้งผลและส่ง LINE แบบ best effort
```

**จุดเน้นในการพูด**: หากอุปกรณ์ชิ้นใดไม่พร้อม รายการทั้งหมดจะไม่ถูกสร้าง

## สไลด์ 9 — Flow การคืนอุปกรณ์

```text
Admin เปิดรายการ active
        ↓
เลือกเฉพาะชิ้นที่รับคืนครั้งนี้
        ↓
บันทึกวันคืนและผู้รับคืนรายชิ้น
        ↓
เปลี่ยนอุปกรณ์เป็นพร้อมยืม
        ↓
ยังมีของค้าง? ── มี → รายการยัง active
        └──────── ไม่มี → completed + แจ้ง LINE คืนครบ
```

**จุดเน้นในการพูด**: การเก็บ `returned_at` ที่ระดับ loan item ทำให้คืนบางส่วนได้

## สไลด์ 10 — สถาปัตยกรรมระบบ

```text
Admin / Borrower
       ↓
Flet Web UI (app/ui.py)
       ↓
AppService: สิทธิ์ + กฎธุรกิจ + transaction
       ↓
SQLite Database

ขอบเขตภายนอก: CSV/XLSX, LINE OAuth, LINE Messaging API
```

**เนื้อหาเสริม**

- modular monolith ภายใน process เดียว
- ไม่มี REST API server แยก
- business rule รวมอยู่ที่ service layer
- Docker ใช้บรรจุ runtime สำหรับ deploy แต่ระบบยังเป็น MVP

## สไลด์ 12 — การออกแบบฐานข้อมูล

**กลุ่มตารางหลัก**

- สังกัด: faculties → departments → cohorts → class_groups
- ผู้ใช้: users → auth_sessions
- อุปกรณ์: equipment_categories → equipment_types → equipment_units
- ธุรกรรม: loans → loan_items → equipment_units

**หลักการสำคัญ**

- username, LINE User ID และ asset code ป้องกันค่าซ้ำ
- ใช้สถานะ inactive แทนการลบข้อมูลที่มีประวัติ
- คืนรายชิ้นด้วย `loan_items.returned_at`
- business date ใช้ Asia/Bangkok; timestamp ใช้ UTC

**ภาพที่แนะนำ**: ใช้ ER diagram จาก `docs/project-report-content.md`

## สไลด์ 13 — กฎที่ช่วยรักษาความถูกต้อง

**เนื้อหาบนสไลด์**

- เฉพาะ Admin สร้างรายการยืมและรับคืน
- ผู้ใช้ inactive หรือมีรายการเกินกำหนดยืมเพิ่มไม่ได้
- วันครบกำหนดต้องไม่ก่อนวันยืม
- อุปกรณ์ต้อง active และ available ทุกชิ้น
- ห้ามอุปกรณ์ซ้ำในรายการเดียว
- transaction เดียวครอบคลุม loan, items และสถานะอุปกรณ์
- ปิดชนิดอุปกรณ์ไม่ได้หากยังมีชิ้นที่ถูกยืม
- LINE ล้มเหลวไม่ทำให้ธุรกรรม rollback

## สไลด์ 14 — ผลลัพธ์และการทดสอบ

**ผลลัพธ์ที่ตรวจสอบได้**

- มีหน้าจอและ flow สำหรับ Admin และผู้ยืม
- schema SQLite 11 ตาราง
- รองรับ persistent login, LINE, import และ Docker runtime
- automated tests 15 กรณีผ่านทั้งหมด ณ วันที่จัดทำเอกสาร
- Python compile check ผ่าน

**ตัวอย่างเรื่องที่ tests ครอบคลุม**

- atomic loan และ partial return
- overdue guard และ inactive equipment
- session และ reset password
- LINE linking และ reminder deduplication
- CSV/XLSX import validation

**ข้อควรระบุ**: implementation plan ระบุว่าการทดสอบ LINE callback/push กับ channel จริงยังไม่เสร็จ

## สไลด์ 15 — จุดเด่น ประโยชน์ และข้อจำกัด

**จุดเด่น/ประโยชน์**

- เส้นทางทำรายการสั้นและค้นหาข้อมูลได้
- ติดตามอุปกรณ์รายชิ้นและคืนบางส่วนได้
- ลดความเสี่ยงของข้อมูลไม่สอดคล้องด้วย transaction
- แยกสิทธิ์และรักษาประวัติด้วย inactive status
- LINE เป็นส่วนเสริมที่ไม่รบกวนธุรกรรมหลัก

**ข้อจำกัด**

- เป็น MVP และไม่ได้ออกแบบสำหรับ production scale
- ไม่มี booking, approval, fine, damage/lost และ audit log
- reminder พึ่ง process ที่ทำงานอยู่และไม่มี retry queue
- SQLite บน hosting ต้องมี persistent filesystem
- ยังไม่มีผลทดสอบกับผู้ใช้จริงหรือ performance benchmark

## สไลด์ 16 — สรุปและแนวทางต่อยอด

**สรุปบนสไลด์**

- ระบบครอบคลุมวงจรข้อมูลผู้ใช้ อุปกรณ์ ยืม คืน และประวัติ
- transaction และ validation เป็นแกนของความถูกต้อง
- บทบาทชัดเจนและรองรับ LINE เป็นช่องทางเสริม
- เหมาะกับ MVP ของสาขาวิทยาการคอมพิวเตอร์ตามขอบเขตที่กำหนด

**แนวทางต่อยอดที่อิงจากข้อจำกัดปัจจุบัน**

- ทดสอบ LINE กับ channel จริงและจัดทำหลักฐาน
- เพิ่ม automated UI/integration test
- ประเมิน usability กับผู้ใช้จริงและวัดผลก่อน–หลัง
- วาง persistent storage สำหรับ environment ที่ deploy
- พิจารณาฐานข้อมูลและ scheduler ที่เหมาะสมหากต้องขยายเกิน MVP
